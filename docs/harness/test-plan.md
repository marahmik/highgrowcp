# Test Plan: 퇴사자 근무기록 관리자 조회

자동 테스트 인프라가 없는 저장소이며, 사용자가 2026-07-29 수동 E2E 예외를 승인했다. 구현 전 아래 결정적 시나리오를 검증 기준으로 고정한다.

## Acceptance Criteria Mapping

### AC1 — 퇴사자 카드 버튼
- 관리자 직원관리 탭의 활성 멤버·승인 대기·밴 목록에는 `근무기록` 버튼이 없다.
- 퇴사자 목록의 각 카드에는 `근무기록` 버튼이 있다.

### AC2–AC3 — 관리자 전용 상세 경로와 데이터 범위
- 퇴사자 카드의 버튼을 누르면 선택한 `store_members.id`를 포함한 `/admin/resigned/:memberId/history` 경로로 이동한다.
- 전체 관리자는 새로고침과 직접 URL 진입에서도 상세 페이지를 볼 수 있다.
- 전체 관리자가 아닌 매장 관리자는 직접 URL을 입력해도 `profiles.role='admin'` 전용 보호 조건이 자식을 마운트하지 않고 `/my`로 이동시켜 페이지와 데이터를 볼 수 없다.
- 상세 페이지는 `store_members.id`와 `role='resigned'`를 함께 확인한다.
- 확인된 멤버십의 `user_id`, `store_id`, 월 시작일, 월 종료일을 스케줄 쿼리에 모두 적용한다.
- 동일 사용자의 다른 매장 스케줄과 같은 매장의 다른 사용자 스케줄은 표시하지 않는다.

### AC4 — 조회 전용
- 일정표는 잠금 상태이며 셀 선택으로 편집 UI가 열리지 않는다.
- 저장 동작을 제공하지 않는다.

### AC5 — 기록 없는 달
- 기록이 없는 달로 이동해도 페이지가 유지된다.
- 빈 일정표와 총 근무 `0일`을 표시한다.

### AC6–AC7 — 잘못된 대상과 권한
- 존재하지 않는 멤버십 ID는 무한 로딩이 아닌 오류 상태를 표시하고 스케줄을 렌더링하지 않는다.
- 활성·승인 대기·밴 등 `role!='resigned'`인 멤버십 ID로 직접 진입해도 오류 상태를 표시하고 스케줄을 렌더링하지 않는다.
- 전체 관리자가 아닌 매장 관리자는 직접 URL로 진입해도 관리자 상세 UI와 데이터를 볼 수 없다.

## Edge Cases
- 퇴사일이 비어 있는 퇴사자도 페이지를 조회할 수 있다.
- 같은 사용자가 여러 매장 소속 이력을 가진 경우 현재 카드의 매장만 표시한다.
- 월 이동 중 이전 요청 결과가 새 월 화면에 잘못 남지 않는다.

## Manual Fixtures / Prerequisites
- `profiles.role='admin'`인 전체 관리자 계정
- `profiles.role='user'`이면서 `store_members.role='admin'`인 매장 관리자 계정
- 한 매장에서 `role='resigned'`인 멤버십과 선택 월의 월초·월말 근무기록
- 비교용으로 같은 사용자의 다른 매장 기록, 같은 매장의 다른 사용자 기록, 이전 달 말일·다음 달 1일 기록
- 기록이 없는 월과 `role!='resigned'`인 멤버십 ID
- 기대값: 선택 월 1일·말일만 포함하고 인접 월 기록은 제외하며, 합계는 `work_type`이 있는 표시 기록 수이다. 퇴사일 이후 기록은 기존 퇴사일 설정 동작이 삭제하므로 별도 숨김 규칙을 추가하지 않는다.

## Verification
1. `npm run build`
2. `npm run lint`
3. `npm run dev`로 실행 후 전체 관리자 계정으로 로그인한다.
4. 직원관리 → 퇴사자 목록 → 근무기록 → 이전/다음 월 이동을 확인한다.
5. 대상자·매장명·퇴사일, 일정표 잠금, 월 합계, 빈 달, 월초·월말 포함 및 인접 월 제외를 확인한다.
6. 활성 멤버 또는 존재하지 않는 멤버십 ID로 직접 진입해 오류 상태와 데이터 미노출을 확인한다.
7. 로그아웃 후 매장 관리자 계정으로 로그인하고 같은 상세 URL에 직접 진입해 `/my`로 이동하며 데이터가 보이지 않는지 확인한다.
8. 브라우저 네트워크를 느리게 설정하거나 이전/다음 월을 빠르게 연속 선택한 뒤, 최종 월·일정표·합계가 같은 월을 가리키는지 확인한다.
