# Test Plan: 운영 무변경 유지보수

## 승인·경계

사용자의 변경 진행 승인은 직전 대화의 운영 코드·DB·배포 무변경 범위에 대한 승인으로 적용한다. 기존 완료 seed는 재개하지 않고 이번 유지보수용 새 task로 추적한다. 운영 서비스·키·계정은 사용하지 않는다.

이번 실행 코드는 기존 기능의 회귀 테스트와 PR 검증뿐이다. 새 앱 동작을 구현하지 않으며, 이미 올바른 기존 경로는 테스트 추가 시 통과할 수 있다. 누락된 보안 경계는 기대하는 차단을 테스트하고 실제 기존 결함 때문에 실패하면 그대로 남긴다. 잘못된 정책을 고치거나 테스트를 skip/약화하여 통과시키지 않는다. 테스트 민감도는 임시 메모리 DB에서 INSERT·UPDATE 잠금 트리거를 각각 제거했을 때 같은 차단 assertion이 실패하는 것으로 확인한다.

## AC 매핑

- AC1: 마이그레이션 001–008의 의존성을 문서와 대조한다. 005의 memo 선행 조건과 locked 참조, 타입에만 있는 퇴사·밴 필드를 명시한다. 신규 설치용 완전한 스키마가 없음을 숨기지 않는다. 수정된 상대 링크와 확인용 읽기 전용 SQL을 검증한다.
- AC2: 수정된 제품 설명·탐색 링크를 실제 README와 대조한다. 범용 하네스 예제는 앱 요구로 오인해 삭제하지 않는다.
- AC3: PR 전용 워크플로 구문·트리거·최소 권한을 확인하고 각 실제 명령을 로컬 실행한다. 배포 job, 운영 시크릿과 네트워크 DB 접속은 추가하지 않는다.
- AC4: node:test와 개발 전용 PGlite로 실제 기존 SQL을 메모리 PostgreSQL에 적용한다. auth 역할·UID 환경과 누락된 두 stores 필드만 명시적 테스트 fixture로 제공한다. authenticated는 NOSUPERUSER NOBYPASSRLS로 실행하며 성공·차단 결과와 저장 효과를 함께 확인한다.
- AC5: 앱·기존 마이그레이션·기존 배포 파일의 해시를 작업 전후 비교한다. 기존 lint 오류는 숨기거나 다른 범위 파일을 고쳐 없애지 않는다.
- AC6: `git push --dry-run --porcelain` 결과로 작업 브랜치 목적지를 확인한다. 실제 push나 설정 변경은 하지 않는다.

## DB 시나리오

1. 역할을 변경하지 않은 일반 직원의 직접 매장 생성, 월별 잠금 변경, delete_user RPC는 차단되며 대상 데이터가 보존된다. 전체 관리자는 해당 작업을 수행할 수 있다. 별도로 직원의 자기 프로필 관리자 승격이 차단되는지 검증한다.
2. 잠금이 없으면 직원의 본인 요청 생성·수정은 성공한다. 근무 타입 지정과 다른 사람 요청 생성은 차단된다.
3. 월별 잠금과 매장별 잠금을 각각 독립적으로 켜면 같은 날짜의 일반 직원 INSERT·UPDATE가 차단되고 저장된 데이터가 변하지 않는다. 잠기지 않은 인접 월과 승인된 다른 매장은 계속 쓸 수 있고, 잠긴 달 안팎으로 날짜를 이동하는 경계도 검증한다.
4. 해당 매장의 승인된 매니저와 전체 관리자의 허용 작업은 잠금에서도 성공한다. 다른 매장 경계는 기존 실제 정책에 맞춰 검증한다.
5. 시나리오 간에는 트랜잭션 rollback 또는 새 fixture로 상태를 격리한다. 테스트 DB는 매번 memory://이며 close한다.
6. 자기 관리자 승격 및 잠긴 달에서 다른 달로 이동은 기존 SQL에서 허용되어 보장되어야 할 차단 테스트가 실패한다. 이를 통과하는 구현으로 고정하지 않으며, 운영 정책 수정은 별도 승인 범위다. 다른 매장 매니저 본인 요청 INSERT 허용은 임시 smoke에서 관찰하고 UPDATE와 구분해 문서화한다.

## 실행 및 증거

- `npm run test:db`: 기존 DB 권한·잠금 동작 회귀 검증.
- `npm run build`: 기존 앱 빌드. 운영 URL·키가 필요한 실행은 하지 않는다.
- `npm run lint`: 기존 전체 lint 결과를 오류 위치·개수와 함께 기록.
- 새 워크플로 구문·문서 링크 검증, 보호 대상 해시 비교.
- 임시 smoke: 테스트 DB를 생성해 직원 잠금 차단을 직접 확인하고, 메모리 DB에서 트리거 제거 후 같은 assertion의 실패로 민감도를 증명한다. smoke 파일은 남기지 않는다.
- 독립 reviewer와 verifier의 결과를 수신한 뒤 완료 보고한다. GitHub 호스팅 runner, 실제 운영 UI·Auth·Realtime 검증은 수행한 것으로 주장하지 않는다.
